# Expected failure modes

Status: all business/provider handling below is **PLANNED**. This map describes intended behavior, not existing retry/fallback implementation. [OPERATIONS_ARCHITECTURE.md](OPERATIONS_ARCHITECTURE.md) owns recovery objectives, thresholds and runbook; [ARCHITECTURE.md](ARCHITECTURE.md) owns response/idempotency contracts. [ROLLBACK.md](ROLLBACK.md) distinguishes code and data effects.

| Failure | User impact | Data impact | Detection | Expected handling | Recovery | Current status |
|---|---|---|---|---|---|---|
| Supabase unavailable | Protected views/posting unavailable | Uncommitted work cannot persist; committed result may be unknown | Dependency checks, sanitized errors, operation status | Fail safely, retain input, no fake success or local financial commit | Restore dependency; reconcile durable operation identity before retry | PLANNED |
| Supabase slow | Delayed lists/posting | Locks/timeouts or unknown commit outcome | Query/pool/lock latency and deadlines | Bounded budgets; conflict/retryable errors without leaking SQL; no unbounded transactions | Diagnose pool/query/locks; replay only safe/idempotent operation | PLANNED |
| Cloudinary unavailable | Upload/download/preview unavailable | Metadata must not claim nonexistent available bytes | Provider errors and manifest reconciler | Pending/unavailable stage, preserve selection/input, no public fallback | Idempotent staged retry/reconciliation; recover originals if necessary | PLANNED |
| Vercel/API unavailable | Requests fail or disconnect | Server may have committed before response was lost | HTTP/uptime/error monitoring | Explicit failure/unknown outcome; no “saved” before confirmation | Roll back compatible code/config if approved; read durable outcome | PLANNED |
| Supabase Auth unavailable | Login/refresh/verified access fails | No new authority may be inferred from stale client data | Auth verification/refresh errors | Fail closed; distinguish expired session from unavailable dependency safely | Recover provider; reauthenticate/reverify; never bypass RBAC | PLANNED |
| Database transaction failure | Operation rejected | All financial/business/success-audit effects roll back together | Commit/constraint/conflict result | No partial success; bounded retry only for safe known conflicts | Correct input/conflict; original idempotency key reconciles uncertainty | PLANNED |
| Partial external operation failure | File/invite looks pending | Remote object/identity may exist without completed app linkage | Durable stage/outcome + reconciler | Grant no accidental membership/file availability; retain retry state | Retry/compensate eligible external stage with audit; never erase required evidence | PLANNED |
| Backup runner failure | Usually no immediate UI effect | Protection age grows; latest partial set unusable | Failed run plus independent cutoff-age verifier | No success seal/heartbeat; bounded retries and operator alert | Catch-up dispatch/operator fallback per operations runbook | PLANNED |
| R2 unavailable/upload/storage failure | Usually no immediate UI effect | Independent generation cannot seal | Storage readback/member/monitor errors | Retain earlier valid points; report degraded recovery | Recover store/access and capture complete new set; no false freshness | PLANNED |
| Stale backup | Work continues with increasing loss exposure | RPO objective may be missed | Four-hour stale warning, six-hour breach | Escalate and consider limiting affected writes; never reset cutoff to job time | Restore capture/fallback; record breach and actual loss window | PLANNED |
| Corrupted/incomplete backup | Recovery may fail | Missing/poisoned records/files | Hash/size/archive/inventory checks and restore drills | Reject generation; do not overwrite last usable point | Choose verified known-clean set, investigate, remediate/retest | PLANNED |
| Email/invite failure | Staff cannot complete invitation/reset | Provider identity may exist but membership must remain controlled | Delivery/provisioning status and safe errors | No account enumeration or accidental activation; preserve durable invite intent | Retry/reissue authorized invite/reset with current callback policy | PLANNED |
| Browser/client loses connectivity | Form save appears failed/unknown | Persisted server result may differ from local view | Network failure/reconnect and status lookup | Retain safe input; label unknown; no offline financial success | Query original operation identity, then reconcile/retry; avoid fresh-key resubmit | PLANNED |
| Duplicate request | Repeat button/retry | Risk of duplicate finance/audit/cash | Durable key/outcome and fingerprint | Same key/content returns authorized original outcome; changed content conflicts | Reauthorize and resolve original operation; no second cash effect | PLANNED |
| Concurrency conflict | Stale edit/remaining balance changed | Must not overbill/overallocate/lose Owner | Version/lock/constraint/serialization result | Safe conflict, preserve input, revalidate all affected targets | Reload/review effective state; bounded transaction retry where valid | PLANNED |
| Unexpected deployment regression | Broken UI/API/auth behavior | Code rollback may leave data/schema changes | Smoke/error/security checks and comparison to known-good commit | Contain risky writes; stop rollout; follow approval boundary | Compatible code/config rollback or forward fix; separate data reconciliation | PLANNED |
| Audit capture failure | Sensitive operation fails safely | No unaudited committed success or false success log | Audit writer/transaction error | Roll back sensitive mutation; safe denial stream remains separate | Restore durable writer, reconcile original operation, test redaction/integrity | PLANNED |
| Wrong environment/preview configuration | Unexpected access or failed dependency | Production leakage/write risk | Environment/project ID validation and isolation tests | Fail closed before provider use; never silently use production fallback | Correct reviewed config; assess/contain exposure if any | PLANNED |

Never blindly retry a non-idempotent financial action or treat a provider timeout as proof of rollback. Preserve evidence and report uncertainty. No V1 offline financial synchronization is implied. Promote a row to IMPLEMENTED/VERIFIED only with code/config and scoped execution evidence, as defined in [THREAT.md](THREAT.md#control-status-and-assets). Link expected failure behavior and observed tests in feature/bug records only when [AGENTS trace criteria](../AGENTS.md#featurebug-trace-rule) apply, or in a subsystem Defense before shipping.
