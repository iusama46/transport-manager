# PostgreSQL persistence boundary

Runtime: **Node.js**, never Edge. Future Route Handlers call services; services authorize and validate workflows before invoking domain repositories. Repositories take an explicit `DatabaseContext` (the exported database or transaction context), encapsulate parameterized persistence operations, and return domain persistence results. No BaseRepository, generated CRUD, business entity, auth authority, HTTP or UI concerns belong here. Shared/mobile/client code cannot import this server-only directory, even transitively.

Services own `database.withTransaction(async (tx) => ...)` and pass **that same tx** to every participating repository. All work must be awaited inside the callback. Commit on success; rollback on callback/query/control failure; release always; discard on rollback or commit acknowledgement failure. A swallowed query failure still aborts. Context expires at callback exit. No nested transactions/savepoints: calling the same database object's pool query/transaction inside its transaction is rejected via async-local context. Reuse tx explicitly; separate independently constructed adapters are not a nesting mechanism. Default isolation is PostgreSQL READ COMMITTED; future reviewed concurrency use cases may begin with `tx.query("SET TRANSACTION ISOLATION LEVEL SERIALIZABLE")`, explicit locks/version predicates and durable idempotency. No automatic retries: a failed COMMIT acknowledgement may have committed. Reconcile durable operation identity before retrying a mutation.

Trusted constant/allowlisted SQL goes in repositories; values always use `$1`, `$2`, ... parameters. Never interpolate request values, identifiers, sort directions or operators. Dynamic identifiers require a closed server-owned allowlist; parameters cannot represent identifiers. The API intentionally accepts SQL text; it is an internal capability, not an injection sanitizer. Do not use transaction control through context.query, named prepared statements, session SET/search_path, session advisory locks, LISTEN or persistent temp tables through the transaction pool. Future verified tenant/RLS context must be transaction-local and established by authorized service composition, never client assertions. No role, RLS, tenant or audit protections are provisioned here.

`NUMERIC/DECIMAL` (OID 1700), `BIGINT` and date-only values are text at this boundary. Numeric arrays need an explicit parser: pg-types 2.2.0 otherwise uses parseFloat. This pool delegates numeric/date arrays to its existing text-array parser, retaining dimensions/nulls. No global parser mutation, binary/row-mode or prepared-name query options are exposed. Send exact decimal inputs as validated strings, never Number/parseFloat; introduce a reviewed exact decimal/domain type when financial calculations are implemented. Row type parameters describe results and do not validate them. JSON/JSONB use the driver's JSON parser: SQL-generated JSON numbers can already lose precision. Cast numeric values to text before JSON construction, or select typed numeric columns directly; never persist financial truth as JSON number. Physical precision/rounding/constraints remain future domain decisions.

`DatabaseError.code` is one of unique, foreign_key, check, conflict (serialization/deadlock/lock unavailable), unavailable (known connection/resource errors), unknown. No raw provider message, SQL, values, constraints, URL or cause is retained. Query/control failures normalize here; application callback errors propagate for service handling. Unrecognized driver timeouts may be unknown. Future API adapters must select safe response codes/messages and never serialize errors/stacks or configuration objects. Error category is not evidence of a mutation's commit outcome.

The exported database is lazy. getPool validates Phase 1.1 configuration on invocation; no sockets at import/build, no Auth SDK/key dependency. One module-scoped pool per warm instance, max 2, min 0, 5s acquisition/idle, 300s lifetime, 15s client query timeout. Transactions set LOCAL 10s statement, 3s lock, 15s idle-in-transaction timeouts; these provisional bounds need actual workload validation. Remote TLS always verifies certificates/hostname, using system roots or optional reviewed PEM CA; URL options cannot override it. Vercel's attachDatabasePool lifecycle adapter is registered once to preserve idle cleanup under Fluid compute; it supplies no business background job. Pool count multiplies by instances/deployments and must be measured against provider/host limits. Hot reload can create fresh module pools; bounded idle/lifetime cleanup limits old instances. No endpoint is exposed; `checkDatabaseConnection()` is an internal SELECT 1 capability, not an authorization/role/isolation test.

Live TLS, privileges, pooling, transactions and connectivity remain unverified until explicitly authorized isolated integration. Provider selection does not authorize connecting to production.
