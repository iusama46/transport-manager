This is the practical actor/entry-point register. [SECURITY.md](SECURITY.md), [PERMISSIONS.md](PERMISSIONS.md), [AUDIT.md](AUDIT.md) and [OPERATIONS_ARCHITECTURE.md](OPERATIONS_ARCHITECTURE.md) remain authoritative for detailed controls. Update the relevant row and evidence when implementation changes; link it from feature/bug/Defense records.

## Control status and assets

PLANNED = required design with no implemented acceptance evidence. IMPLEMENTED = code/configuration exists with a path/commit reference. VERIFIED = a specific test/exercise passed, with date, commit, environment and result; verification is scoped and expires when relevant behavior changes. Promote a runtime control only with that evidence. Current domain/Auth/RBAC/DB/file/backup controls below are **PLANNED**. Existing ignored env files/config-name validation are implemented foundations with dated evidence in ENVIRONMENT/TASKS; they do not verify future provider bundles or production access.

Assets: identity/session credentials, Company-private contacts/identity documents, financial/operational history, immutable audit, original file evidence, backups and recovery keys. Trust boundaries: untrusted client/Expo → server; verified identity → app permissions; service → tenant-scoped DB; service → Cloudinary; operations CI → recovery store; operators → production.

## Verification and acceptance

Use TEST_PLAN T15/T23–T36/T56–T57/T77–T78/T102–T118 and relevant feature tests. Add positive and adversarial direct-request tests for the specific boundary; mocked UI tests do not prove DB/file isolation. Before ship, clear material assumptions in HANDOVER, identify residual risks/owners and link actual evidence in the [Defense brief](defense/TEMPLATE.md). This register is not a penetration-test report or proof that runtime mitigations exist.
