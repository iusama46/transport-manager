# Reviewed PostgreSQL migrations

Phase 1.2 has **no SQL migration or business schema**. Plain SQL uses the already selected `pg` access approach without another schema/ORM library. This directory owns migration sources; the application never runs them.

Name each future file `YYYYMMDDHHMMSS_description.sql` in UTC, strictly increasing, lowercase snake_case. Use lowercase snake_case SQL names, schema-qualified references and explicit named constraints. Private application schema, Company constraints, RLS, protected Owner and audit grants must be designed/reviewed in their authorized phases; nothing here provisions them.

`node scripts/db-migrations.mjs` lists ordered filenames and SHA-256 checksums **offline**. `node scripts/db-migrations.mjs --sql` emits a reviewable psql bundle. No credentials, driver, DB discovery or application env is consumed. Empty history produces a comment only, with no metadata schema. Generation is not migration execution or approval.

The bundle uses one explicit transaction, transaction advisory lock, bounded lock/statement waits, private `tm_migrations.applied` metadata and checksums. It rejects missing/edited applied history and out-of-order additions, skips identical applied files, and records each successful migration in the same transaction. All work rolls back together on failure. Applied files are immutable; fixes use new files. No automatic down/destructive rollback or schema push. SQL files must contain trusted SQL only: no psql commands, transaction control, session changes, or nontransactional DDL (including CREATE INDEX CONCURRENTLY). These last restrictions require human SQL review; the generator is not a SQL security parser. Do not mix independently generated partial bundles.

After explicit human review of the **concrete generated SQL**, target/project identity, privileges, compatibility, effects and verification/recovery plan, an authorized operator may execute a saved bundle using `psql -X --set=ON_ERROR_STOP=1 --file=/path/to/reviewed.sql`. Connection configuration comes from protected operations custody (e.g. approved service/passfile with verified TLS); do not put URLs/passwords in shell arguments, source or logs. Use a separate migration identity and direct connection (reviewed session pooler fallback for IPv4); never the transaction-pool runtime URL or runtime role. No web/build/install/deploy script applies migrations. Production execution requires its own explicit authorized human action under [AGENTS](../../AGENTS.md), [CONSTRAINTS](../../docs/CONSTRAINTS.md) and [ROLLBACK](../../docs/ROLLBACK.md).

First application into any target requires separately reviewed role/schema ownership and metadata grants. Runtime must have no access to the migration ledger or DDL, no ownership/superuser/BYPASSRLS, and no protected generated Data API exposure. Destructive changes require known-good code, independent backups and tested restore/forward-fix consideration; code revert does not reverse data. Replay/rollback/lock/checksum behavior against PostgreSQL remains **UNVERIFIED** until an authorized isolated integration test. No migration has been generated for application or executed in Phase 1.2.
