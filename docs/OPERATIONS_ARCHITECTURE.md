# V1 authentication, documents and operations architecture

Reviewed: 16 October 2026. Status: selected provider/security and recovery architecture; B1 CLOSED. Development Ready v1.0: YES; Production Ready: NO. Documentation requirements only; no infrastructure or application controls are implemented by this audit. [FINAL_ARCHITECTURE_AUDIT.md](FINAL_ARCHITECTURE_AUDIT.md) owns the readiness verdict. This document supersedes earlier unresolved-provider and mandatory $0 production wording.

## Selected providers and trust boundaries

Next.js/TypeScript on Vercel provides the UI and thin `/api/v1/*` REST handlers. Authorized server services coordinate repositories/transactions against Supabase PostgreSQL. Supabase Auth identifies users; application User/Membership/Role/Permission/resource rules authorize them. Cloudinary stores document bytes in development and production; PostgreSQL stores metadata only. Supabase Storage is not selected. An appropriate paid production plan is acceptable; no service is purchased or deployed here.

Every protected entry follows authentication → active application User and Membership resolution → Company validation → permission → resource/field/relationship authorization → business validation → query/mutation → durable audit where applicable → safe response. Server-rendered reads use the same authorized services. UI gates and provider JWT role claims cannot establish business privileges. Preserve [DATA_MODEL.md](DATA_MODEL.md) I01–I44 and A01–A17 without redesign.

## Supabase Auth contract

- Invite-only email/password accounts. Disable provider public signup and anonymous users as well as omitting public registration UI/API. Only protected, permissioned staff provisioning can invite an identity and establish an eligible membership. Email confirmation follows configured provider policy; invite possession alone never grants membership/Owner authority.
- Verify tokens server-side against the correct environment/project issuer, signature, audience and expiry using maintained provider verification. Never trust decoded-only tokens, client `getSession()` data, email address, editable user metadata or an asserted Company as authority. Link provider subject to stable application User identity; retain historical actor IDs after deactivation/renaming.
- Web uses Supabase SSR cookie/session refresh integration, HTTPS Secure cookies and explicit SameSite settings. Apply CSRF token/origin validation to cookie-authenticated mutations. Do not assume standard browser Supabase refresh cookies are HttpOnly; assess XSS/CSP and client token exposure at integration. Never store privileged credentials in those cookies. Request-specific auth clients must not share user state between Vercel requests.
- Future Expo uses bearer access tokens for the same REST API, with refresh credentials in platform secure storage. Restrict CORS to approved web origins; mobile bearer access does not require public wildcard credentialed CORS. Reject ambiguous conflicting cookie/bearer identities.
- Refresh, logout, reset and verification callbacks use exact environment redirect allowlists and no arbitrary return URL. Recovery responses avoid account enumeration and have rate/abuse limits. Production transactional email delivery must be configured/tested before launch.
- Check current application activation, membership and grants on every operation; deactivation/revocation must take effect even with an unexpired JWT. Logout invalidates the app session as well as provider refresh credentials. At integration, validate provider session existence for the JWT session identifier or maintain a durable app revocation record; signature verification alone cannot prove a session was not revoked. Test concurrent refresh and stale-cookie behavior.
- Bootstrap the first Owner through a restricted operator-only provisioning path, never first public signup, email matching or a normal role grant. Establish the active protected Owner membership before enabling Company operations. Provider and application changes require durable provisioning state/retry/reconciliation, because Auth admin calls and application transactions do not share an atomic commit. Incomplete provisioning grants no access. Preserve A13 for every subsequent Owner transfer/deactivation.

Provider evidence: [signup/confirmation configuration](https://supabase.com/docs/guides/auth/general-configuration), [SSR sessions and cache/client isolation caveats](https://supabase.com/docs/guides/auth/server-side/advanced-guide). Session verification and revocation must be demonstrated during implementation; no successful security test is claimed here.

## Cloudinary document contract

Client → authorized Next.js API/service → Cloudinary. Every upload/download/metadata lookup checks the same-company typed parent, applicable document/identity permissions and lifecycle. Raw provider IDs, filenames and possession of a URL are never permission. Keep API secrets/signing/admin access server-only. No unsigned public upload preset or public sensitive document delivery.

At integration, configure a bounded allowlist (initial document formats PDF, JPEG and PNG), per-file and whole-request size limits below the host body ceiling, content-signature checks and decoded-media/resource limits. Fail closed if limits are absent. Reject HTML/SVG/executable content and extension/MIME mismatches; quarantine unvalidated content and use an appropriate malware inspection path before availability. Sanitize original filenames (basename, no path/control characters, bounded length), generate opaque object identifiers and avoid PII in URLs. Serve untrusted originals as attachments with correct Content-Type and nosniff; previews must be equally protected.

Persist Company, typed parent/version, Document/DocumentType, safe original filename, verified MIME/format, byte size, checksum, uploader and timestamps, availability/lifecycle, Cloudinary asset ID, public ID, resource/delivery type and immutable version/reference. Keep the term `public_id` as a provider identifier, not a public-access policy. File bytes never enter PostgreSQL. Replacement appends a new file version; do not overwrite historical invoice/proof evidence.

Protect originals **and derived previews** using authenticated delivery or an equivalently verified private path. A `private` original alone can leave derivatives public. Ordinary signed CDN URLs have no inherent expiry and can be shared. After parent authorization, use the provider's time-limited private-download API with explicit expiry, resource/delivery type and attachment disposition; test supported PDF/image delivery and expiry in the selected account. Short-lived links are bearer capabilities until expiry: do not log/store them as durable metadata or expose them in public caches. If a provider configuration cannot protect both original and derivatives, deny delivery until corrected. No `noindex`, random filename or ordinary URL signature substitutes for access control.

Staged lifecycle under A17: authorize/reserve pending metadata and operation identity → upload/validate object → finalize verified version/manifest plus audit transaction → mark available. A retry never duplicates evidence. Failed stages remain unavailable and enter reconciliation. Authenticated provider callbacks must be signature-checked and deduplicated; client upload results alone cannot finalize metadata. Archive preserves bytes and historic access under permissions. Explicit permitted deletion first validates history/holds/dependencies, records durable removal intent and audit, then removes/invalidate objects with retries and records a tombstone; external deletion cannot be made atomic by PostgreSQL. Do not destroy required historical evidence.

An idempotent scheduled reconciler compares pending/removal states, provider inventory and database manifests. After a documented grace interval, delete only proven unreferenced temporary objects with audit; never infer an orphan from one missed page or transient DB failure. Alert on missing referenced versions and failed cleanup. Concrete cadence/grace/retries are implementation configuration. Backup retention/deletion reconciliation must honor authorized removal and legal requirements.

Provider evidence: [access controls and expiring private downloads](https://cloudinary.com/documentation/control_access_to_media). Cloudinary is selected for both environments; account settings and file security remain implementation acceptance work.

## Deployment and environment isolation

| Environment | Supabase database/Auth | Cloudinary | Secrets, URLs and data |
|---|---|---|---|
| Development | Dedicated development project/local environment with synthetic data | Separate development product environment/credentials | Localhost callbacks only where needed; app-local ignored env files |
| Preview/Staging | Dedicated nonproduction project, never production; isolated namespaces/fixtures for simultaneous previews | Dedicated nonproduction product environment/credentials | Vercel Preview scope, approved preview callbacks, protected preview access; no production keys or copied private data |
| Production | Dedicated production Supabase project and Auth issuer | Dedicated production product environment/credentials | Vercel Production scope, approved canonical HTTPS domain, exact production callbacks and restricted operators |

Prefer a stable protected staging URL for Auth callbacks over broad wildcard previews. Fork/untrusted builds receive no privileged secrets. Validate target project/environment identifiers before any migration, seed, upload or backup/restore. Names/folders alone are not credential isolation. Builds/prerendering must not query private production data. Production secrets must be absent from preview scopes; use environment-specific DB runtime/migration/backup roles and Cloudinary keys. Restore exercises use isolated targets and block production callbacks/email/jobs.

Only intentionally public Supabase project URL and publishable/anon key are potentially browser-safe after a reviewed public allowlist; they confer no business access. Database URLs/passwords, Supabase secret/service-role keys, JWT signing secrets, Cloudinary API secret and credential-bearing CLOUDINARY_URL are server-only. Cloud name/API key are identifiers, not signing secrets, but need no client exposure for this server-mediated design. Current templates stay comment-only and validator rejects all public prefixes until actual integration adds reviewed names/validation/tests. No provider key is bundled today because no integration exists; future `server-only` import barriers and bundle inspection are required.

Deploy Next.js Node handlers using bounded pools, transaction-local tenant context, verified DB TLS and request/query/lock budgets. No long-lived local state, in-memory financial locks or process timers establish durability. Vercel's currently documented 4.5 MB request/response limit requires bounded server-mediated uploads; choose smaller limits accounting for multipart overhead. Larger payload requirements must trigger an explicit storage/transport review before enabling them. Background exports, reconciliation and backups need durable execution, authenticated triggers, retries and alerts; no process-after-response guarantee is assumed. [Vercel function limits](https://vercel.com/docs/functions/limitations).

Configure canonical domain, HTTPS, protected environment variables, security headers, private/no-store authenticated responses (including Set-Cookie), sanitized structured logs and correlation IDs. Health checks expose minimal liveness; restricted readiness/operational checks cover DB/Auth/Cloudinary connectivity, jobs and backup age without leaking credentials. Record deployment/version evidence, alert routes and runbooks. Roll back to a known-good deployment with compatible schema; database changes require separate reviewed migration and recovery/forward-fix planning. Code rollback never restores database/files automatically. Paid hosting eligibility is not a development blocker.

## Backup and disaster recovery — authoritative V1 specification

Status: **B1 CLOSED — architecture selected, 16 October 2026. Development Ready v1.0: YES.** This section is the single recovery specification; other documents link here. Decisions below formalize the user’s proposed baseline, with a three-hour capture interval to leave headroom for the six-hour RPO objective. No runner, bucket, monitor, secret, backup or restore is provisioned/executed by this documentation task. Development Ready != Production Ready.

### Selected design and objectives

| Responsibility | Selected V1 design |
|---|---|
| Primary database recovery | Supabase Pro production project with at least Small compute and seven-day PITR add-on; verify enabled window/capacity at provisioning |
| Independent backup runner | GitHub Actions, ephemeral GitHub-hosted Linux runner, protected default branch of a dedicated private operations repository; scheduled and operator workflow-dispatch entry points |
| Independent destination | Private Cloudflare R2 Standard S3-compatible bucket in a separately administered recovery account, outside Supabase/Cloudinary/Vercel; public access/custom delivery domains disabled |
| Capture cadence | Every three hours, UTC 00:17, 03:17, 06:17, 09:17, 12:17, 15:17, 18:17, 21:17; one complete database/Auth/document generation per successful run |
| Retention | All three-hour generations for seven days; first complete generation each UTC day for 35 days; first complete daily generation each UTC month for 400 days |
| Encryption | TLS with certificate verification plus mandatory age public-key encryption of dumps, private manifests and file bytes before leaving the runner; R2 provider encryption at rest as an additional layer |
| Key custody | Decryption identities in an MFA-protected recovery vault and separate offline emergency copy; neither in R2, GitHub Actions nor the application; separate automation signing/storage credentials |
| Accountable operator | System Owner / Designated Technical Administrator, with a designated backup administrator for absence/emergency coverage |
| RPO | <= 6 hours for the latest fully sealed independent database/Auth/document checkpoint; objective, not a scheduler/provider guarantee |
| RTO | <= 4 hours from incident declaration to validated approved traffic cutover; objective until measured at representative volume |
| Independent monitoring | Better Stack checks every five minutes against a protected Cloudflare Worker that verifies R2 generation evidence; separate GitHub failure notices and sealed-generation heartbeat |
| Restore testing | Full isolated pre-production exercise, quarterly after launch, and after material recovery changes; monthly decryption/archive-integrity drill |

Managed PITR is the first recovery path for database-only incidents while the Supabase account remains available. Independent R2 generations are the path for provider/account loss, corruption beyond the managed window, or complete coordinated recovery. S3 object APIs, PostgreSQL logical archives, portable JSON manifests and age-encrypted bytes keep the recovery format independent of the selected store. Changing adapters later must preserve these objectives and controls.

Supabase’s official documentation currently offers daily managed backups on Pro/Team/Enterprise, PITR as an add-on with minimum Small compute, and second-level restore granularity within its available recovery window. Enabling PITR replaces daily backups; do not promise simultaneous daily snapshots or downloadable physical archives. Daily custom-role passwords are excluded; file bytes are outside database recovery. Our chosen seven-day PITR window and the independent logical path must both be confirmed at provisioning. Finer managed DB granularity is distinct from complete-system RPO: it does not recover a Cloudinary file absent from independent copies. [Supabase managed backups/PITR](https://supabase.com/docs/guides/platform/backups).

**RPO meaning:** an incident may lose up to six hours of committed business/Auth/document changes after the latest usable independent cutoff. Restoring a deliberately older clean generation after long-undetected corruption may lose more; report actual loss and obtain incident approval rather than claim the target was met. GitHub can delay/drop scheduled jobs and disable inactive public-repository schedules. Six-hour starts alone leave no completion/retry margin; V1 therefore selects three-hour starts, a one-hour normal sealing budget, four-hour freshness alert and six-hour breach threshold. This is our engineering choice under the proposed baseline, not a GitHub timing SLA. If production measurements cannot meet it, increase capacity/cadence or move the runner before launch. [GitHub schedule limitations](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule).

### Independent PostgreSQL generation

1. Acquire a durable generation lease and unique run ID; reject overlapping capture of the same slot and never cancel an in-flight valid generation just because a scheduled run arrives. Lease expiry/recovery is bounded by the one-hour run budget. Record source project/environment, application/migration commit and PostgreSQL/client versions. Use primary DB direct TLS or session pooler connection; never transaction-pooler session assumptions. Pin the PostgreSQL client major version to the deployed server major.
2. A coordinator holds one repeatable-read exported PostgreSQL snapshot. Both application archive and Auth data archive, plus document/reference and count/control-total manifests, use that same snapshot. Record snapshot acquisition UTC time conservatively as the recovery cutoff, not job completion/upload time. Serialize schema releases against backup capture to avoid inconsistent DDL/configuration. Independent dumps taken at unrelated times are not a coherent generation. [PostgreSQL synchronized dumps](https://www.postgresql.org/docs/current/app-pgdump.html).
3. Use direct `pg_dump` in custom archive format, explicitly listing all application-owned schemas, the complete `auth` data, migration history and required catalogs. Capture application schema/data/sequences/RLS/grants/functions and restore inventory for extensions/roles. A separate Auth archive is data-only against target-managed Auth tables; retain its full table/row inventory. Capture application-auth customizations from reviewed migrations, not a blind overwrite of provider-managed DDL. Application binary documents are not PostgreSQL large objects; fail inventory validation if an unexpected blob/extension-owned dependency is omitted.
4. The export identity is a dedicated backup-reader login with `pg_read_all_data` and BYPASSRLS, no application DML/DDL/role administration, separate from runtime/migration identities. Review/revoke unnecessary inherited PUBLIC function/schema capabilities; default read-only mode alone is not a security boundary. Credentials only in the private protected operations environment, never a Vercel/client/public-repository secret. Abort on unreadable tables/RLS/schema mismatch; no “successful” partial-tenant dump. [Supabase dedicated export-role guidance](https://supabase.com/docs/guides/troubleshooting/pg_dump-fails-with-query-would-be-affected-by-row-level-security-policy-1d5783).
5. Validate archive readability/table coverage, expected nonzero Company/Owner/Auth data after provisioning, per-table counts and finance/audit/document control totals from the shared snapshot. An actually empty first setup requires explicit operator baseline approval, not an auto-learned empty threshold. Encrypt using pinned age recipient public keys and inventory plaintext hashes inside the encrypted manifest; retain only safe ciphertext size/hash/status externally. Hashes/ETags alone are not a tested restore.
6. Complete Cloudinary copies for the snapshot manifest, encrypt private configuration inventory and upload all generation objects to R2. Re-download and verify ciphertext hashes/lengths, independently list/HEAD every member and check reference completeness. Only then publish a signed immutable completion manifest. A partial upload never advances freshness or becomes selectable for restore. Commit success metadata/heartbeat only after storage verification; record failure separately with no credential/data payloads.

The Supabase CLI default dump excludes managed schemas and is schema-only unless data/roles are explicitly requested. It is not the selected automatic exporter. No assumption is made that a default CLI dump covers Auth. Role definitions/configuration are captured separately from role passwords; approved migrations plus the encrypted privilege/extension inventory reconstruct them on a compatible managed target. [CLI dump exclusions](https://supabase.com/docs/reference/cli/supabase-db-dump).

### Supabase Auth recovery boundary

Supabase stores Auth records in its PostgreSQL `auth` schema; users and hashed passwords can be migrated through a suitable full backup or explicit export/import. V1 preserves all Auth tables in the cutoff inventory, including user UUIDs/identities/verification/ban and any stored session/refresh/MFA state, and preserves application User-to-provider-subject links. Password hashes are sensitive recovery data, not raw passwords and not application audit payloads. Do not restore only `auth.users` while omitting related state. [Official Auth migration scope](https://supabase.com/docs/guides/troubleshooting/migrating-auth-users-between-projects).

**Normal DB backups are not a hosted project configuration export.** Maintain a versioned encrypted configuration inventory and an independently accessible credential vault covering project/organization access, Auth provider/signup/verification/password/session settings, site and redirect URLs, SMTP settings/templates and SMTP secret reference, hooks/customizations, signing-key configuration/key IDs and recovery/rotation instructions, API keys, DB role secrets, deployment variables, DNS/domain and monitoring configuration. Capture non-secret configuration after every approved change and include its version in each generation. No promise that a provider-managed signing private key can be exported: provision fresh target signing/API credentials and reconfigure clients. V1 does not use Supabase Vault/pgsodium to store application secrets; adoption later requires separate root-key recovery review. Provider guidance warns that encrypted data alone does not contain those root keys. [Managed-target restore/configuration caveats](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore).

Recovery creates a compatible Supabase target, lets the provider establish its managed Auth schema, restores matching Auth data with the supported version-specific process, restores application migrations/links, and recreates Auth settings/secrets outside the DB dump. Target service/schema compatibility and user/password continuity must be proven in the full restore exercise. Do not copy obsolete managed migrations/ownership blindly.

**Fail closed on sessions:** invalidate restored sessions/refresh credentials and outstanding recovery/invite tokens, use fresh signing keys on a replacement project, clear app sessions and require new sign-in; reissue necessary invites/resets deliberately. A same-project recovery must also revoke pre-incident sessions and enforce an application session epoch/revocation boundary. This prevents an old checkpoint from resurrecting revoked access. Reapply documented post-cutoff account deactivations, role removals and security changes from the independently retained incident/access-change record before traffic cutover; if that evidence is unavailable, disable affected/all staff access pending Owner review. Reprovision MFA enrollment where key compatibility requires it. Browser and future Expo configurations must target the correct new issuer/API keys; membership/Company/resource checks still apply. Credentials/configuration reconstruction and deliberate reauthentication are selected behavior, not an assumption of seamless session continuation.

### Cloudinary independent document recovery

Enable Cloudinary automatic original/version backups on the selected production account, with a paid plan sized for storage, Admin API limits and recovery volume. Native backup defaults to off; own external storage integration is paid and documented for specific cloud providers. **Do not assume native S3 integration accepts R2**. V1 instead uses authenticated API inventory/download into our own R2 pipeline. Native recovery is useful for deleted/changed sources during collection, not the independent destination. [Cloudinary native backup scope/plan behavior](https://cloudinary.com/documentation/backups_and_version_management).

Each application AttachmentFile version remains immutable and maps to Company, typed parent/resource/version, Document/type, asset ID, public ID, resource/delivery type, Cloudinary version, safe filename, verified MIME/bytes/hash and lifecycle. The private generation manifest captures these associations from the DB snapshot, not current search labels. Paginate authenticated provider inventory for image/video/raw and all used delivery types; fetch each manifest-referenced original/version through authenticated download, or backed-up-version download if it has since changed/deleted. Do not rely on a public URL, a ZIP containing only visible images, or regenerated previews as original evidence. [Cloudinary inventory API](https://cloudinary.com/documentation/admin_api#resources), [original/version download methods](https://cloudinary.com/documentation/image_upload_api_reference#download_backup).

Each recovery generation is **self-contained**: its own encrypted DB/Auth/config/manifest and every required original/file-version object under its unique prefix. Previously verified ciphertext for an unchanged immutable file may be copied within R2 into the new generation; verify copied hashes and retain its encryption key ID. Download changed/new versions once from Cloudinary. This avoids repeated source downloads while making deletion/restore/retention independent of shared-blob garbage collection. Per-generation required files include archived/historical evidence still referenced by that cutoff; derivatives may be regenerated under the original protected delivery rules. Never infer files are disposable because their master is archived.

DB/file consistency uses the snapshot manifest plus immutable version hashes, rather than a cross-provider transaction. Uploads after cutoff belong to a later generation. Pending uploads remain pending; available files must have bytes. Before any explicit permitted permanent Cloudinary deletion, verify protected copies exist for every retained generation that needs the version and record the removal/tombstone; missing source and missing backup is a failed checkpoint/incident, not an auto-repair by dropping metadata. Provider-only orphans are listed separately and cannot invent a Company/resource link. Removal/holds remain subject to the finalized legal/business/history policy; an urgent lawful erasure is a deliberate documented exception, never routine backup pruning.

During restore, load DB/Auth into a clean nonpublic target first; then upload required original bytes to a clean private Cloudinary environment with preserved public IDs/types where supported. New asset IDs/provider versions may differ: record an explicit old-to-new mapping and update storage-location metadata only through the controlled recovery mapping, preserving historical business identity/snapshots/audit. Verify hash/size/MIME, parent/Company/version association, availability and private original/preview access. No public fallback for a missing document. Missing required historical evidence fails acceptance; seek an earlier complete generation or record an approved recovery exception and actual loss before any restricted cutover.

### Retention, object protection and cost envelope

| Tier | Minimum retained complete points | R2 lock / pruning rule |
|---|---|---|
| Frequent | Every three hours for seven days, about 56 points | Unique frequent prefix, minimum seven-day bucket lock |
| Daily | First complete point each UTC day for 35 days, about 35 points | Self-contained copy in daily prefix, minimum 35-day lock |
| Monthly | First complete daily point each UTC month for 400 days, about 13–14 points | Self-contained copy in monthly prefix, minimum 400-day lock |

Promotion copies and verifies all members before its own completion seal; a missing daily/monthly point alerts and retries the next valid source that day/month. Copy creation starts the destination retention clock. No automatic business/audit purge follows from rotating backup generations.

A separate weekly retention job holds only the target bucket's object credentials, never DB/Auth/Cloudinary credentials or encryption private keys. It deletes expired generation prefixes only after verifying locks/holds, daily/monthly promotions, fresh complete recovery points and at least two later complete generations. It never deletes the last known complete point or advances retention from a failed job. No unconditional lifecycle rule deletes complete generations; safe temporary/unsealed objects may expire after seven days if no active lease. Alert if pruning fails or expired complete objects persist over seven days beyond their retention without a recorded hold. Holds stop pruning with an operator record and reviewed extended lock. Do not remove a bucket lock to make a normal retention job pass.

R2 lock rules prevent overwrite/deletion during retention, including ordinary object-write compromise. They are **not irreversible compliance WORM against the Cloudflare account administrator**, who can remove rules. Keep bucket/account administration outside capture and retention runners, MFA-protect break-glass access, require a second authorized human for lock weakening/destructive account actions and independently alert on policy/inventory changes. [R2 bucket locks](https://developers.cloudflare.com/r2/buckets/bucket-locks/), [R2 object versus admin permissions](https://developers.cloudflare.com/r2/api/tokens/).

Storage is roughly the compressed encrypted full database+Auth+required-documents size multiplied by about 56 + 35 + 14 retained points, plus promotion overlap, metadata and failed-run headroom. For illustration, a 1 GB complete generation can approach 105 GB retained before overlap; this is an assumption, not a measured size/quote. Source DB extraction is eight runs/day, and Cloudinary source transfer covers new/changed versions; R2 intra-store copies, requests, GitHub minutes/disk and monitoring plans also consume resources. Do not assume S3-compatible means every AWS-specific operation/lock feature is supported. Measure one-hour sealing and four-hour restore at representative growth, provision headroom and budget before launch. If exceeded, change capacity/runner or record an explicit architecture revision; never reduce required history/capture silently.

### Encryption, credentials and custody

- Require verified TLS for PostgreSQL, Cloudinary, S3 and monitoring APIs. Use R2 automatic encryption at rest **and** age encryption under separately held recovery public recipients for every private dump, file and detailed manifest. R2's provider-managed keys alone do not protect against bucket-account read compromise. Only an opaque completion manifest (run/cutoff IDs, encrypted member keys/lengths/hashes, key IDs and status) is unencrypted and Ed25519-signed; omit tenant names/PII/SQL/provider secrets. [R2 encryption](https://developers.cloudflare.com/r2/reference/data-security/), [age encryption implementation](https://github.com/FiloSottile/age).
- Capture runner holds only the DB export password, minimum available Cloudinary read/export key, bucket-scoped object read/write key, dedicated completion-signing key and success/failure notification credentials. Public age recipients/verification keys are pinned in reviewed configuration. If Cloudinary cannot restrict export credentials to read-only in the chosen plan, isolate that product environment/key, keep the residual broader power explicit and test credential scope; never give the runner account owner credentials. Signing is separate from encryption: the runner cannot decrypt old backups.
- Storage capture privileges are not described as append-only: object write can include destructive object actions. Locked, unique generation keys protect older points; automation cannot edit bucket locks or account policy. Read-only verifier/restore-storage credentials are separate; recovery target administrative credentials are time-limited operator access, never normal backup-run credentials. The export reader necessarily sees all Company/Auth data and must never serve normal requests.
- The System Owner owns access reviews and recovery approval. The Designated Technical Administrator maintains service credentials, pipeline and restore evidence. An independent authorized custodian holds emergency access and the second decryption recipient/offline recovery kit. Names/contact assignments live in a restricted operations register, not Git. The vault and offline sealed copy must remain accessible if GitHub/Supabase/Cloudinary/Cloudflare accounts fail. Neither encryption private identities nor their passphrases belong in the bucket, Actions secrets or application source.
- Rotate automation/storage/export/signing credentials at least every 90 days and immediately after exposure, staff access changes or incidents; test new access then revoke old tokens. Rotate active encryption recipients annually and on compromise. Record which generations use which key, retain old identities until all needed generations expire, and perform administrator-controlled re-encryption of carried-forward files before retiring their old keys. Re-encryption never makes leaked historical plaintext secret again. Test recovery of both current and retained keys during drills.
- No payload/dump/private manifest is a GitHub artifact, Actions cache, PR output or log. Disable command tracing and sanitize tools/errors; keep plaintext only on the isolated ephemeral runner during capture, clean temporary files and never run production secrets in pull_request/pull_request_target/fork jobs. Pin reviewed action/container/tool versions and immutable commits, restrict workflow edits with branch protection/review, set minimum GitHub token permissions, use a private operations repository and separate production capture from untrusted application CI. Scheduled capture uses branch-restricted secrets without a per-run human approval queue; production restoration is a separate explicitly approved operation.

### Monitoring, alerting and failure handling

Better Stack is the selected external alert/on-call service; the monitor is outside GitHub and Cloudflare so a missing workflow or unavailable recovery account can still cause an alert. Every five minutes it requests a secret-header-protected, no-store Cloudflare Worker verification endpoint. The Worker uses a bucket-scoped S3 read-only credential (not a general write-capable R2 binding) and signature verification public key, no DB/Auth/Cloudinary/decrypt/write powers; it lists recent immutable seals and HEADs all encrypted members for completeness/size, not a mutable “last success” flag. The API returns health/category/cutoff age only. Worker/account/network failure is unhealthy. A separate configuration-read credential permits daily bucket lock/policy audit; never combine it with write/admin authority.

| Signal | Threshold / required behavior |
|---|---|
| Capture/upload/storage/Cloudinary synchronization failure | Immediate failed-job notice through GitHub notifications plus Better Stack incident notification; no completion heartbeat/seal; bounded two retries with backoff within the one-hour budget |
| Slow/missing capture | Job exceeding one hour fails; external age check alerts when the newest complete snapshot cutoff is older than four hours, regardless of workflow status |
| RPO breach | Cutoff age >= six hours is a critical recovery-objective breach; display degraded recovery, preserve evidence, operator initiates catch-up and limits affected writes if continuing would compound unprotected loss |
| Empty/small/corrupt archive | Zero bytes, unreadable archive, missing expected tables/Auth/Owner or manifest member fails immediately; >50% unexpected size/count drop against the last seven valid points requires operator adjudication, never automatic baseline reset |
| Integrity | Every capture verifies ciphertext full readback SHA-256/size; external monitor checks signed seal/member presence/length; daily inventory validates expected manifests/promotions/lock configuration; monthly drill decrypts and reads archives/file hashes |
| Retention/promotion/holds | Missing daily/monthly promotion after 24 hours, lock weakening or unexpected object removal alerts immediately on audit; expired unheld points remaining > seven extra days alerts; missing inventory audit heartbeat >26 hours alerts |
| Monitor failure/silence | Separate sealed-generation heartbeat expected every three hours + one-hour grace; independent HTTP endpoint check also catches missing initial heartbeat/worker/R2 failure; test alert routing before first production data |

Notifications go to the System Owner / Designated Technical Administrator on-call group by email and configured mobile/push escalation; acknowledgment is required within 15 minutes, escalating to the backup administrator if unacknowledged. At four-hour freshness alert, run an authorized catch-up via dispatch. If GitHub is unavailable, the administrator uses the pinned recovery toolchain on a clean controlled workstation to capture/encrypt/upload with separately issued temporary access; same format/checks/locks apply. This fallback is operator initiated, not a concealed second always-on runner. A provider outage can still miss RPO: record the breach and mitigate, never reset the freshness timestamp. Backup monitoring contains no customer contents, signed downloads or credentials. [Better Stack heartbeat behavior](https://betterstack.com/docs/uptime/cron-and-heartbeat-monitor/).

A heartbeat is sent only after validated storage completion. Even a valid signature proves pipeline provenance rather than correct business data; retained older generations, counts/control totals and real restore exercises address corrupted/compromised producers. Test negative cases for forged success, stale seal, missing object, poisoned manifest, stopped scheduler, email/push failure and disabled monitor before launch.

### Threat model and independent failure domains

| Threat | Selected mitigation and residual risk |
|---|---|
| Leaked Actions secrets / malicious workflow | Private protected operations repo, pinned reviewed dependencies, no fork/PR secrets, export-reader isolation, no decrypt/admin keys, signed manifests and immutable locked generations. Runner compromise can exfiltrate live read data/poison future points; revoke, investigate and select last known clean retained generation |
| Compromised bucket read/write credentials | Application-side encryption/private key separation, bucket-scoped keys, object locks, unique keys and signed inventory. Attacker may disrupt future writes; independent monitor alerts; rotate keys |
| Compromised production DB or Cloudinary account | Different recovery account/credentials, independent DB/Auth/file generations and retained older clean cutoffs. Capture cannot repair source corruption; restore validation chooses a clean point and reports actual loss |
| Accidental/ransomware-style deletion | No source deletion synchronization into backups, locked time tiers, separate prune credentials/holds and deliberate restore/cutover approval |
| Destructive account administrator | Recovery-account separation, MFA, dual approval for lock weakening, external alerts and break-glass custody. R2 admin/account loss is a residual failure domain; R2 locks do not promise survival of an all-powerful admin or simultaneous loss of all providers |
| Corrupt/stale/incomplete backup | Full readback hashes, shared-snapshot counts/control totals, sealed manifest, external cutoff-age checks, monthly decryption and quarterly full restore. Hash checks cannot substitute for restoration |
| DB/Cloudinary mismatch | Version-specific snapshot manifest, independent original bytes per generation, deletion escrow check, explicit remapping and missing-file fail-closed behavior |
| Lost/compromised encryption key | Two independently custodied recipients, offline recovery kit, annual/incident rotation, retained-key inventory and tested decryption; never store keys with objects |
| Reintroduced revoked access after rollback | Fresh signing/session boundary, explicit reauthentication, independent access-change register and Owner review before cutover |

Supabase backup alone != complete independent recovery: it shares its provider/account failure domain and does not include Cloudinary bytes or all hosted service configuration. Cloudinary account storage alone != independent document recovery: provider/account deletion, missing backups or corrupted source can remove evidence while PostgreSQL still references it. GitHub is execution, not a backup destination; Vercel code rollback is not data restoration. R2 separates source-provider failures; Better Stack separates alerting from scheduler/store failure; independent vault/offline key custody separates access recovery. The six-hour objective covers loss of primary services while a valid independent generation/key path survives, not simultaneous total loss of every recovery custodian/provider or arbitrarily old corruption.

### Restoration runbook and human approval

1. **Declare incident.** System Owner / Designated Technical Administrator records incident ID, UTC start, affected services, suspected compromise and scope. Start the RTO clock at declaration; discovery delay is recorded separately. Preserve evidence; notify the designated operators through the approved incident process.
2. **Contain writes.** Put the app into maintenance/read-only mode, stop posting/numbering, uploads/deletions, invitations/email/jobs and retries where needed. Revoke compromised credentials without deleting evidence. Maintain a write/cutover fence so only one environment can later accept writes.
3. **Approve recovery scope.** The Technical Administrator proposes database-only PITR or full independent recovery, target/cutoff, expected data loss and fallback. The System Owner deliberately approves any production restoration **before** a destructive restore action; this approval is never inferred from a backup job or this architecture task. The executor and approving Owner are separate authorized humans where staffing permits; otherwise record the accountable Owner’s explicit approval. No automated production restore.
4. **Select point.** Choose a complete signed generation at/before the last known clean state, inspect member inventory/key availability/retention and decrypt/verify hashes. For managed PITR, confirm available WAL window; do not restore DB newer than available file evidence without a verified complete file manifest. Record expected RPO from cutoff; do not label an incomplete set usable.
5. **Provision clean target.** Create isolated compatible Supabase/Cloudinary targets with public access/notifications/jobs disabled; validate environment IDs, engine/Auth version, extensions, schema/migration compatibility, vault/key access and capacity. Never test against production. Allocate the first 30 minutes to containment/access/point selection, then aim to have target provisioning and DB/Auth restoration completed within two hours elapsed.
6. **Restore PostgreSQL.** Recreate approved roles/extensions/settings and restrictive default grants; for a logical restore, establish the application schema, load same-cutoff Auth data into the compatible managed schema before dependent application User/membership rows, then restore application financial/history data and sequences in dependency order. Alternatively perform the approved managed restore. Follow supported managed-target ownership/privilege handling; run fail-on-error, record all skips and do not blindly execute a backup from a compromised producer. Preserve invoice/sequence/idempotency outcomes and enforce constraints before exposure. Validate all app-to-Auth foreign-key links and restored constraints after loading; temporary restore-only privileges/triggers must return to their documented secure state before validation. No superuser assumption or undocumented overwrite of managed schemas.
7. **Recover Auth dependencies.** Reconfigure invite-only settings, redirects/site URL, email templates/SMTP/hooks and fresh signing/API/DB credentials from the independent inventory/vault. Invalidate old sessions/tokens, reapply known deactivations/revocations and verify stable User UUID/membership links; do not send reset/invite messages during an isolated test.
8. **Recover Cloudinary.** Restore required originals/versions from encrypted generation bytes into the private target, verify hashes and controlled old/new provider mappings, reconcile DB file metadata/status/tombstones and rebuild protected previews. Aim for file restoration to complete by three hours elapsed; original/private delivery remains blocked until validation.
9. **Validate isolation/security.** Restore RLS/grants/service boundaries, active membership and last-active-Owner protections. Run allowed/denied cross-Company reads/writes/counts/files/export, revoked-user/session and direct-data API tests; no temporary public grant remains.
10. **Validate financial invariants.** Reconcile I01–I44 and relevant A01–A17 evidence: effective invoice/note versions and Trip coverage, no overbilling, payment/credit/allocation/payable/account totals by Company/currency, paired transfers, historical quantities/rates/FX, unique numbering and durable retry outcomes. Compare to cutoff control totals, not current live master settings.
11. **Validate audit.** Reconcile event counts/ranges/actor snapshots and durable business-event links; verify redaction and append-only restrictions. Record recovery work in a separate immutable incident/access record and append a new permitted recovery event after restoration; never rewrite old audit history to hide rollback.
12. **Validate references and authentication.** All available Documents resolve to correct private original bytes/parent/Company/version; missing/pending references are explicit. Test invite-only sign-in, configured verification/reset/refresh/logout, fresh-session revocation and Owner access using approved synthetic accounts; password continuity testing must not expose real users’ hashes/passwords. Future Expo follows the same API/issuer update rules.
13. **Smoke test.** Start the compatible application version in the isolated target, verify a protected read and controlled synthetic operation with audit/idempotency, API/selector behavior, dependency health and no secrets in logs/bundles. Recheck config/callback/email/job and reconciliation fence. Reserve the final hour for validation and approval, not unbounded repairs.
14. **Approve and cut over.** System Owner explicitly approves production traffic cutover only after documented checks/loss/objective results; point Vercel/server/Auth/Cloudinary configuration and domain to the approved environment, keep old writers fenced, smoke test and resume jobs in a controlled order. Pending external retries are reconciled against restored operation identities, never blindly replayed. If validation fails, remain contained or approve a recorded restricted exception; do not claim normal recovery passed.
15. **Record result.** Record declaration/discovery/cutoff/restore/cutover times, measured RPO/RTO, missing/lost operations/files, hashes/counts/balances, roles/auth/doc checks, approvers/executor/tool versions, root cause, credential changes and follow-up. Re-enable backups/monitoring against the new environment, verify a new sealed generation, and preserve the original incident evidence.

RTO includes provisioning, decryption/copies, DB/Auth/file restoration, validation and human approval through traffic cutover. Growth, GitHub/Cloudinary rate limits or delayed approval can miss four hours; report measured duration and remediate capacity/process before production acceptance. No guaranteed availability SLA or previously tested restoration is asserted.

### Restore exercises, evidence and closure

Before production: implement the pipeline/monitors/permissions, produce multiple valid generations with documents and Auth, and run a **full isolated restore from R2 with primary provider credentials unavailable**. Also exercise managed PITR, retention/locked-delete denial, expired/rotated keys, stopped/delayed schedule and failure alerts. Verify password-user continuity plus forced reauthentication, wrong-Company/archived-history/private-file behavior and financial/audit invariants. Record a complete artifact manifest, source cutoff, versions/data volume, timings, approvers, expected/actual data loss, SHA-256/count/control-total results and every failed check. Test actual alert delivery, not just configured addresses.

Monthly after launch: decrypt and inspect a rotating frequent/daily/monthly generation on a clean isolated operator environment, verify archive structure, sampled original file hashes and every referenced encryption key generation. Quarterly, after material PostgreSQL/Auth/storage/schema/key/pipeline changes and after a recovery incident: perform the full DB/Auth/Cloudinary restore with the same evidence and measure end-to-end RPO/RTO. Missed objectives or integrity gaps create corrective work; do not launch until pre-production remediation/retest passes. After launch, declare degraded recovery, prioritize correction/capacity change and retest before reporting compliance. Keep restricted drill evidence for 400 days; no production data/keys in Git.
